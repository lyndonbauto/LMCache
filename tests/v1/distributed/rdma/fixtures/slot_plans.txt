# Shared slot-planning cases, read by both planners.
#
# The slot arithmetic exists twice on purpose -- in C++ for the production
# fetch path, and in Python so Track C's tests need no native build. Each
# side has its own tests; what neither can catch alone is the two drifting
# apart, which would surface as a slot naming a record the write side never
# produced. This file is the one thing both read, so a divergence fails here.
#
# Consumed by:
#   tests/v1/distributed/rdma/csrc/slot_plan_dump.cpp   (C++ SlotPlanner)
#   tests/v1/distributed/rdma/test_slot_plan_parity.py  (Python FetchPlanner)
#
# Format, one directive per line, `#` and blank lines ignored:
#
#   case  <name>
#   kernel <group_id> <kv_size> <num_slots> <hidden_dim> <element_size> <layer_id>...
#   place <chunk_id> <group_id> <dest_offset>
#   caps  <max_record_bytes> <max_write_bytes>
#   end
#
# Kernel groups are concatenated into their object group's payload in the
# order declared here, so declaration order is part of the case.
#
# Cases are chosen for where the two implementations could plausibly
# disagree, not for coverage of either alone: plane striding, how a plane is
# cut into records, and what happens when one geometry is not enough.

# The ordinary case: key and value planes a whole layer dimension apart,
# several chunks, a plane that is exactly one record.
case uniform_two_plane_exact_record
kernel 0 2 16 128 2 0 1 2 3
place 0 0 0
place 1 0 1048576
place 2 0 2097152
caps 4096 1048576
end

# A 10000-byte plane against a 4096-byte cap. Cutting as cap-plus-remainder
# gives 4096/4096/1808; cutting into the fewest equal pieces gives
# 3334/3334/3332. Only the second is servable, because a sink carries no
# record-relative source offset, so every piece but the last must be exactly
# the record size the write side used.
case plane_needing_three_uneven_pieces
kernel 0 2 10 500 2 0 1
place 0 0 0
caps 4096 1048576
end

# Two pieces where the naive split would be 4096 + 904 and the correct one
# is 2500 + 2500.
case plane_splitting_evenly_in_two
kernel 0 2 25 100 2 0 1 2
place 0 0 0
place 1 0 1048576
caps 4096 1048576
end

# One object group holding kernel groups of different geometry. This is the
# case a single flattened stride gets wrong: the second group's layers would
# be strided by the first group's plane size. It is also the case the writer
# used to give up on, sharding by byte count because no one plane size
# described the payload.
case hybrid_kernel_groups_in_one_object_group
kernel 0 2 8 64 2 0 1
kernel 0 2 32 64 2 2
kernel 0 1 8 64 4 3 4
place 0 0 0
place 1 0 1048576
caps 4096 1048576
end

# A hybrid object whose second kernel group needs uneven pieces. The writer
# cuts each kernel group against its own plane size, so record numbering
# must restart its piece arithmetic at the second group rather than carry
# the first group's one-piece-per-plane stride into it.
case hybrid_later_group_split_into_uneven_pieces
kernel 0 2 8 64 2 0 1
kernel 0 2 10 500 2 2 3
place 0 0 0
place 1 0 1048576
caps 4096 1048576
end

# Object groups of different shapes, one of them itself hybrid, as a
# Mamba/GDN model produces: records are numbered per object, so each group's
# numbering starts at zero regardless of the other's.
case hybrid_object_groups_of_different_shapes
kernel 0 2 16 128 2 0 2
kernel 1 1 24 256 2 1 3
kernel 1 2 4 64 2 5
place 0 0 0
place 0 1 1048576
place 1 0 2097152
place 1 1 3145728
caps 4096 1048576
end

# Two object groups of the same payload size, laid out differently. The
# writer picks a record layout by payload size, so it cannot tell these
# apart and must fall back to byte-count sharding for both; the Python side
# must refuse to name their records rather than assume alignment.
case same_size_groups_laid_out_differently
kernel 0 2 8 64 2 0 1
kernel 1 1 32 64 2 2
place 0 0 0
place 0 1 1048576
caps 1500 1048576
end

# Layers spread across two object groups with interleaved global indices, so

# MLA: the engine format drops the leading K/V dimension, so a layer is one

end

# Layer indices in tensor order rather than ascending. Position in the

end

# A sliding-window group placed for only its trailing chunks, alongside a
