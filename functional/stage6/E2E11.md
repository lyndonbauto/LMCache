| Meta record bins | `nseg=160, seg_b=524288, plane_b=1048576, tot_b=83886080, state=ready, ver=1, wid=<16 hex>, pin=False, created_at` | `nseg=64`, `tot_b=33554432` |
| Segment record | one bin `b`, 524,288 bytes. The same for the first and last chunk of a 64-chunk prompt (P-exact-15), a ragged 48-chunk prompt (P-ragged-19) and a P-shared prompt | same |
| Per layer and chunk | 1 MiB (`plane_b`), so 2 segments per layer | same |

### Is "three kv-sink server processes" still needed?

No. The ledger note dates from the old-server plan, where E4 meant a 3-node layout (see
`stage6/CHANGES.md`, CPU half: three `asd` in `aero-kvsink`). On server `046e8558d`, three
processes would still form a cluster, and LMCache refuses pipelined plans on a multi-node
cluster (N1). One adapter also cannot spread keys over three single-node clusters. The
only reason to grow is capacity, and one node with `data-size 64G` holds the whole corpus
(46.8 GB used). This server hit no size or record limit: no `SERVER_FULL`, no record over
`max-record-size`, and 5 GiB windows registered and served 64-chunk fetches.
